# Cryptographic construction and provenance

Status: experimental, unaudited. No production or post-quantum security level is asserted.

## Existing primitive

The source in `crates/winterwallet-core/src` is copied without algorithmic edits from Blueshift Winterwallet commit `672fc6789b1532ee680f24842d235e0be8737b61`, https://github.com/blueshift-gg/winterwallet (MIT; Dean Little). The manifest is adapted to this workspace. Its own README says it is not formally audited. Its claims are not adopted as independent assurance.

Bunker selects N=32, the full SHA-256 message digest, not Winterwallet's smaller transaction default. There are 32 message scalars and two checksum scalars, each 32 bytes. Chains perform SHA-256 up to 255 times; checksum is sum(255-digest[i]), encoded as two big-endian digits. Public chain endpoints are committed with tagged Merkle leaves SHA256(0x00 || endpoint) and nodes SHA256(0x01 || left || right), duplicating the rightmost node on odd levels. A signature is 1,088 bytes. This is the upstream Winternitz construction, NOT WOTS+, LMS, XMSS, or an asserted NIST-approved Bunker scheme.

The TypeScript port in `sdk/winternitz.ts` uses pinned `@noble/hashes` SHA-256. `fixtures/winterwallet-n32.json` is generated by the included Rust example from a PUBLIC TEST mnemonic. It is not a funded key, runtime default, or production seed. Cross-language tests compare the full key root and signature bytes. Runtime keys use 1,088 independent bytes from `crypto.getRandomValues`; Bunker does not use the upstream custom mnemonic derivation.

## Canonical withdrawal preimage

Concatenate these exact bytes (no JSON, length prefixes, strings, or user-controlled serialization):

| Field | Bytes | Encoding |
|---|---:|---|
| Domain | 15 | ASCII `BUNKER_DEVNET_V1` |
| Program | 32 | Public key bytes |
| Vault | 32 | Public key bytes |
| Nonce | 8 | Unsigned little endian |
| Kind | 1 | 0=SOL, 1=classic SPL |
| Mint | 32 | Zero pubkey for SOL |
| Destination | 32 | Wallet for SOL, exact token account for SPL |
| Amount | 8 | Unsigned little endian base units |
| Next root | 32 | Merkle commitment |

The payload after the first three fields is 113 bytes. Program and vault context plus the devnet-only domain prevent cross-program or cross-vault reuse. The on-chain domain is for this test program only; a future mainnet release needs reviewed domain separation. Solana programs cannot directly obtain a genesis hash; the client pins the genesis, recovery files include it, and all mainnet writes are rejected. The same program/vault/root instantiated on another test fork is not cryptographically independent; never copy authority keys between networks.

## One-time state and rollback

The on-chain root and nonce rotate only after a valid transfer; the transaction is atomic. Replays fail after rotation. Publication of two different signatures under the same key can permit forgery even if only one transaction succeeds. Atomic rotation ALONE DOES NOT solve off-chain key reuse.

The browser uses a mandatory Web Lock plus persistent public intent digest before signing. A signed pending kit (old root, exact payload/signature, next secret/root, recipient) is encrypted, checkpointed, downloaded and re-opened before upload. No old secret is retained in the new kit. A resumed transfer submits identical chunks and identical payload. The next secret can be recovered from the pending kit after confirmation.

These safeguards only coordinate one origin/browser. Stale exported backups, separate devices, cleared browser storage, malicious frontends, same-origin compromise, and chain rollback remain unresolved risks. State encryption does not solve rollback. Review must determine a production signing architecture with durable one-time state, likely outside the general web frontend. Published authorizations have no expiry or cancellation path; destination freezing or permanent transfer failure can trap the current authorization. This is an explicit experimental tradeoff, not production UX.

## Recovery encryption

Web Crypto PBKDF2-SHA256, 600,000 iterations, independent random 16-byte salt; AES-256-GCM with independent random 12-byte IV; AAD `BUNKER_RECOVERY_DEVNET_V1`. The encrypted envelope format is versioned and strictly parsed; file sizes and byte lengths are bounded. Encryption authenticates ciphertext, not the truth of on-chain state. The user must choose a strong password. No reset path exists. Strings and runtime copies cannot be reliably zeroized in JavaScript.

## Required external review

Review the upstream signature security and Merkle commitment, constant-time considerations, random generation, digest and canonicalization, wallet/RPC boundaries, browser dependency supply chain, crash windows, multi-device key reuse, rollback, rent, upgrade authority, and freeze/issuer risks. Passing automated tests is not an audit.
