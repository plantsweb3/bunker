# Cryptographic construction and provenance

Status: experimental, unaudited. No production or post-quantum security level is asserted.

## Existing primitive

The source in `crates/winterwallet-core/src` is copied without algorithmic edits from Blueshift Winterwallet commit `672fc6789b1532ee680f24842d235e0be8737b61`, https://github.com/blueshift-gg/winterwallet (MIT; Dean Little). The manifest is adapted to this workspace. Its own README says it is not formally audited. Its claims are not adopted as independent assurance.

Bunker selects N=32, the full SHA-256 message digest, not Winterwallet's smaller transaction default. There are 32 message scalars and two checksum scalars, each 32 bytes. Chains perform SHA-256 up to 255 times; checksum is sum(255-digest[i]), encoded as two big-endian digits. Public chain endpoints are committed with tagged Merkle leaves SHA256(0x00 || endpoint) and nodes SHA256(0x01 || left || right), duplicating the rightmost node on odd levels. A signature is 1,088 bytes. This is the upstream Winternitz construction, NOT WOTS+, LMS, XMSS, or an asserted NIST-approved Bunker scheme.

The TypeScript port in `sdk/winternitz.ts` uses pinned `@noble/hashes` SHA-256. `fixtures/winterwallet-n32.json` is generated by the included Rust example from a PUBLIC TEST mnemonic. It is not a funded key, runtime default, or production seed. Cross-language tests compare the full key root and signature bytes. Runtime keys use 1,088 independent bytes from `crypto.getRandomValues`; Bunker does not use the upstream custom mnemonic derivation.

## Canonical withdrawal preimage (protocol 2)

`programs/bunker/src/lib.rs::decode_intent` and `sdk/protocol.ts::decodeIntent` enforce the same fixed-width payload. The signed message is exactly 238 bytes: ASCII `BUNKER_WITHDRAW_TEST` (20 bytes), raw program public key (32), raw vault PDA (32), then this **154-byte** payload. Offsets below are zero-based, end-exclusive within the payload:

| Offset | Bytes | Field and encoding |
|---|---:|---|
| 0..1 | 1 | Protocol version, exactly `0x02` |
| 1..33 | 32 | Vault identity used in PDA seeds |
| 33..41 | 8 | Nonce, unsigned little endian; less than u64 maximum |
| 41..42 | 1 | Kind: 0 = SOL, 1 = classic SPL |
| 42..74 | 32 | Mint public key, all zero for SOL |
| 74..106 | 32 | Exact destination public key (token account for SPL) |
| 106..114 | 8 | Positive amount in base units, unsigned little endian |
| 114..122 | 8 | Positive expiry slot, unsigned little endian |
| 122..154 | 32 | Nonzero next-authority Merkle commitment |

No JSON, variable-length fields, padding or alternative integer encodings occur in signed bytes. Unknown versions/kinds, truncated or extra bytes, zero amounts, absent commitments and exhausted nonce encodings are rejected. The next root must differ from the current root and must never have been consumed in this program. The signed id must match the stored vault identity, whose PDA must derive under the executing program id. The destination account and, for SPL, mint account must match the signed keys.

Expiry is inclusive: `Clock::get()?.slot <= expiry_slot`. A signature after expiry is invalid even if cryptographically valid. Slots are not wall-clock deadlines. There is no cancellation instruction and no second-key reveal or expiry recovery escape hatch.

`fixtures/bunker-v2.json` contains public-test encoding, full message, SHA-256 digest, signature and two successive root/nonce rotations. Generate it with `cargo run -p bunker --locked --example protocol_vectors`; both Rust and TypeScript verify it. `fixtures/winterwallet-n32.json` remains the separate upstream primitive vector. The new generator is outside the unchanged vendored core. `vendor/winterwallet-revision.json` pins every upstream algorithm file's SHA-256; tests reject drift. These checks are reproducibility evidence, not independent cryptographic review.

The test domain is not authorization for real funds. Program/vault context prevents cross-program/vault reuse; it does **not** distinguish cloned test chains with identical addresses and state. Solana programs do not directly obtain a genesis hash. The client pins genesis and the recovery blob includes it. Never copy authority keys between networks or forks.

## Atomic one-time state

After verification, the withdrawal instruction creates an immutable 8-byte spent-root PDA at `[b"spent-v2", current_root]`, transfers the exact amount, then updates the existing vault's root and nonce. All three effects commit together. The marker has no close instruction and cannot be reused as a vault or proof account. Its rent is paid by the ordinary fee wallet. Both initialization and rotation require the candidate root's marker to be absent (an empty System-owned prefunded PDA is allowed). A marker prevents reinstalling a revealed root, including in another vault. Independently generate every root; copying an active root between vaults can strand the losing vault.

A second valid signature under the old root fails after one successful withdrawal. SOL remainder stays in the vault PDA; classic SPL remainder stays in accounts owned by that PDA. Both come under the newly installed root **in that same instruction**, including assets not selected for this transfer. No successful withdrawal leaves a remainder controlled by the old root.

Solana transaction failure rolls back the transfer, marker and rotation. It cannot undo off-chain signing or proof publication. On failure the on-chain root may still be the revealed root, while the local key is permanently consumed. Only resubmission of the saved exact authorization before expiry is supported. An expired intent, an irreparable transfer failure, or a crash before the signed checkpoint is saved can permanently lock test assets. A future recovery mechanism needs separate review; silently re-signing is not recovery.

## Canonical encrypted recovery and journal

The v2 encrypted blob is the canonical portable state. It contains version, network/genesis, program, vault id/address, current index, next unused index, nonce and current commitment root. Ready state contains the current secret; pending state contains the exact payload/signature and next secret/root, with no current secret. The root is the chain's active commitment, not a pre-generated tree of future authorities. Nonce equals current index. Ready `(currentIndex=n, nextUnusedIndex=n+1)` becomes pending `(n,n+2)` before submission, then ready `(n+1,n+2)` only after chain confirmation of the expected next root and nonce.

Import and export are explicit user recovery events. Creation downloads a blob; the user re-opens it before initialization. Preparing a withdrawal downloads the pending blob; the user re-opens it before publishing. Import checks the file against the chain and any persistent local journal. Signing never silently creates a missing journal; explicit import is required.

Under a Web Lock scoped to genesis/program/vault, `authorizeWithdrawal` checks the supplied state, decrypts the persisted checkpoint, and checks current chain root/nonce. It persists **consumed** status, advanced next-unused index, exact-message digest and next root, with a read-back check, **before generating any signature**. It then saves the encrypted pending checkpoint. If signing, encryption or persistence fails after consumption, the journal remains consumed. Even an identical message cannot invoke signing again. Retrying reads the saved signature; it does not regenerate it.

Reconciliation has only two outcomes: the old chain state means the pending key stays consumed, or the exact next root and nonce mean recovery can adopt the next key. Other combinations, missing journals during signing, mismatched checkpoints and stale imports fail closed. A consumed orphan without its completed signed blob cannot recover by importing the old ready blob.

Web Locks coordinate only cooperating tabs in one origin with intact storage. Two restored copies there cannot both invoke signing. Separate devices/origins, cleared storage, a malicious frontend, restored browser profiles and rollback can still split-brain and produce multiple signatures. The local-validator test deliberately exercises two independent restored copies: both signatures verify, but at most one different withdrawal is accepted. **This does not make multiple signatures cryptographically safe.** Leaking two messages can permit forgery and must be treated as a broken one-time-key assumption. Durable production signer state remains unresolved.

## Authenticated encryption

Web Crypto PBKDF2-SHA256 with 600,000 iterations and random 16-byte salt derives an AES-256-GCM key. Each export uses a random 12-byte IV and 128-bit tag. Envelope metadata has exactly these fields in this canonical order:

`format="bunker-encrypted-v2", aead="AES-256-GCM", tagBits=128, kdf="PBKDF2-SHA256", iterations=600000, salt=<lowercase hex>, iv=<lowercase hex>`.

AAD is UTF-8 `BUNKER_RECOVERY_TEST_V2:` followed by the compact JSON serialization of that ordered metadata. Ciphertext (including the GCM tag) is lowercase hex in the final envelope field. Parsers validate versions, exact key sizes, decimal indices, field names, metadata and bounded file sizes. The plaintext is serialized in schema order. Root/secret correspondence, vault derivation and pending signature/context are verified after decryption. Password strength matters; no reset exists. JavaScript strings and runtime copies cannot be reliably zeroized. Encryption authenticates stored bytes, not freshness, the frontend, or RPC truth.

## Authorization boundary

The hash signature authorizes this vault withdrawal instruction only. Fee payment, account creation and ordinary Solana transactions still use conventional signatures; Solana runtime/consensus, RPC, program upgrades, browser and wallet trust remain. No end-to-end post-quantum security is claimed. See [Solana transaction semantics](https://solana.com/docs/core/transactions) for ordinary signatures and atomic transaction behavior.

## Required external review

Review the upstream signature security and Merkle commitment, constant-time considerations, random generation, digest and canonicalization, wallet/RPC boundaries, browser dependency supply chain, crash windows, multi-device key reuse, rollback, rent, upgrade authority, and freeze/issuer risks. Passing automated tests is not an audit.
